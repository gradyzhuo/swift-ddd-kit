Framework Migration Guide

swift-ddd-kit  1.4 → 1.5

withUnitOfWork: one atomic write across usecases and aggregates — an upgrade guide for projects that depend on swift-ddd-kit

target: swift-ddd-kit Swift 6.1+ / Ubuntu / macOS 15+ / iOS 18+ ⚠ source-breaking for custom EventStoreClient conformances audience: human + AI agent
version transition
FROM1.4
→
TO1.5

1.5 adds withUnitOfWork { work in … }: every repository.save inside the block is collected and written together when the block returns, or not at all when it throws. Existing usecases, repositories, generated code and the composition root take part unchanged; code that never calls withUnitOfWork behaves exactly as in 1.4. What breaks the build is limited to custom EventStoreClient conformances, exhaustive switches over EventStoreClientError, and a direct swift-kurrentdb requirement below 2.6.1. The public signatures of Usecase, EventStore, EventSourcingRepository and KurrentStorageCoordinator do not change.

Source-breaking changes

These stop existing code from compiling, and the compiler points at each place.

SB1  protocol  EventStoreClient.identity has no default

Custom EventStoreClient conformances (wrappers, decorators, hand-written fakes) must implement var identity: ObjectIdentifier { get }. Inside one unit of work only clients with the same identity commit together. There is no default on purpose: two clusters taken for one would send events to the wrong cluster. LiveEventStoreClient reports the identity of the KurrentDBClient it wraps; every InMemoryEventStoreClient instance is an identity of its own. A wrapper forwards the identity of the client it wraps, and forwards appendAtomically(_:) too (BC1):

struct LoggingClient: EventStoreClient {
    let base: any EventStoreClient
    // ...other requirements...
+   var identity: ObjectIdentifier { base.identity }
+   func appendAtomically(_ batches: [StreamBatch]) async throws -> [StreamBatchResult] {
+       try await base.appendAtomically(batches)
+   }
}

SB2  enum case  New EventStoreClientError cases

CaseThrown when
consistencyViolations([StreamConflict])appendAtomically found streams whose expected revision did not hold; nothing was written. Never empty. KurrentStorageCoordinator turns it into DDDError.commitConflict(conflicts:).
atomicAppendUnsupportedthe conformance relies on the deprecated default of appendAtomically(_:).

An exhaustive switch over EventStoreClientError without a default must handle both.

SB3  dependency  swift-kurrentdb ≥ 2.6.1

swift-kurrentdb 2.6.0 silently dropped custom metadata from events written through AppendRecords, the call a unit of work uses for two or more streams; 2.6.1 carries it, and throws for metadata that is not a JSON object (BC6). If your Package.swift depends on swift-kurrentdb directly, raise the requirement too.

- .package(url: "https://github.com/gradyzhuo/swift-kurrentdb.git", from: "2.6.0")
+ .package(url: "https://github.com/gradyzhuo/swift-kurrentdb.git", from: "2.6.1")

Behaviour changes

The compiler will not point these out They compile unchanged but behave differently, mostly once code runs inside withUnitOfWork. Check each one against your code and tests.

BC1  runtime  Wrappers must forward appendAtomically(_:)

EventStoreClient gains appendAtomically(_:). The protocol extension provides a deprecated default, so an existing conformance compiles, with a deprecation warning; but a unit of work that writes two or more streams through it throws EventStoreClientError.atomicAppendUnsupported at commit. Forward it as in SB1.

BC2  usecase  Publishing right after save

A usecase that calls EventBus.publish right after repository.save publishes before the commit when it runs inside withUnitOfWork, so subscribers can see events that are never written. To be right inside and outside a unit of work:

if let work = UnitOfWork.current {
    try work.onCommitted { try await notifier.send(.quotingCreated(id)) }
} else {
    try await notifier.send(.quotingCreated(id))
}

BC3  client  One KurrentDBClient instance per unit of work

Writes in one unit of work commit together only through clients with the same identity, and the identity is the KurrentDBClient instance, not the cluster. Coordinators built with init(client: KurrentDBClient, eventMapper:) over one instance share the unit of work, so a composition root that passes one client everywhere needs no change. Two instances connected to the same cluster (two KurrentDBPool.borrow() results, say) count as two: the first write through the second one throws DDDError.operationNotAllow. A read through another instance neither binds the unit of work nor sees its staged events, only what the server has: only coordinators whose client has the unit of work's identity see them. A read error through it still fails the unit of work like any store error. A usecase that reads what an earlier usecase in the same block saved needs a repository over the same KurrentDBClient instance.

BC4  repository  The check lives in EventSourcingRepository's default implementations

Inside a unit of work, the default save and purge refuse a store that cannot take part, and errors from store calls in the default find, save, delete and purge fail the unit of work even when the caller catches them. Code that calls store.append or store.purge directly on a non-participating store still writes or purges at once inside a unit of work (a purge is permanent, even when the block then throws), and a repository that overrides those methods gets neither the refusal nor the automatic failure.

BC5  aggregate  Do not reuse aggregate instances after a unit of work

Inside a unit of work, an aggregate's version after save is the revision the commit is predicted to give it. When the server returns another one, the commit logs a warning and succeeds: the server's revision is the true one. That happens, for example, when a soft-deleted stream is recreated: it continues from the old tail + 1 instead of 0. After a block that threw, the instance still reflects the discarded save. Find aggregates again after the block.

BC6  metadata  Metadata inside a unit of work

A unit of work that writes two or more streams sends metadata as protobuf Value (AppendRecords properties) instead of raw JSON bytes, so every save inside a unit of work checks that the metadata encodes to a JSON object. A type that encodes to a scalar (a String-backed enum, say) throws DDDError.operationNotAllow(operation: "save", …) at save, not at commit; nil metadata is not checked, and outside a unit of work such metadata is still written as before.

  • NaN and ±infinity throw EncodingError from the coordinator's JSONEncoder at save, not operationNotAllow, inside a unit of work and outside it, as before 1.5. Inside a unit of work the error also fails it.
  • Numbers are not checked further: inside a unit of work that writes two or more streams each one travels as the nearest Double, so an integer beyond ±2^53, including one beyond 64 bits such as a large Decimal, is stored rounded without an error. Store values whose every digit matters as strings.

Read back, the custom metadata also holds the server's $schema.name and $schema.format keys; decoding into a struct is unaffected, so compare decoded values, not raw bytes or dictionaries.

Behaviour inside a scope

Everything here is new in 1.5 and applies only while withUnitOfWork runs. Outside a scope nothing changed.

How the scope ends

  1. The block returns or throws, and the scope closes at once. From then on work.fail(_:), work.onCommitted(_:) and work.backend(_:identity:make:) throw operationNotAllow, also from a Task started in the block, which still sees the scope as UnitOfWork.current. So a save that runs after the block throws instead of writing.
  2. The block threw (CancellationError included): nothing is committed, no hook runs, the error is rethrown.
  3. The scope was failed (by work.fail(_:) or by a repository error): nothing is committed, no hook runs, and withUnitOfWork throws DDDError.operationNotAllow(operation: "commit", reason: "unit of work failed") with the first cause in userInfos["cause"].
  4. Otherwise the staged writes commit. One stream goes through the same single-stream append as a plain save; two or more go through one AppendRecords call (KurrentDB 26.1+; an older server gives operationNotAllow(operation: "commit", reason: "server does not support AppendRecords (KurrentDB 26.1+)")). A conflict on any stream rejects everything with commitConflict and error.commitConflicts lists every conflicting stream; a purged stream gives streamPurged, also when other streams conflict.
  5. The onCommitted hooks run in registration order, outside the scope (UnitOfWork.current == nil): a save inside a hook writes directly and is not part of the commit. A throwing hook stops the later ones and its error is rethrown, but the commit stands.
Commit errors After commitConflict or streamPurged nothing was written. After any other commit error (transport, atomicAppendUnsupported, a server without AppendRecords) the writes may have landed, for example when the response was lost after the server committed: read the streams before running the block again.

Stores, reads and purge

  • Only KurrentStorageCoordinator takes part. save and purge through a repository over InMemoryEventStore or PersistentEventStore throw operationNotAllow; save does so even when the aggregate has no new events (outside a scope such a save still returns without calling the store). find is never refused. Tests use KurrentStorageCoordinator over InMemoryEventStoreClient: no server needed.
  • KurrentStorageCoordinator.purge throws operationNotAllow(operation: "purge", reason: "not allowed inside a unit of work"), also when called directly. A direct store.purge on InMemoryEventStore or PersistentEventStore is not refused: it purges at once and permanently, even when the block then throws.
  • Reads through a coordinator whose client has the scope's identity see the events the scope has staged, after the server's (read-your-writes). A read never creates, binds or fails on the scope's backend, so a usecase may read through a repository over another KurrentDBClient, but that read sees only what the server has (a read error through it still fails the unit of work, BC3). A usecase that reads what an earlier usecase in the same block saved needs a repository over the same KurrentDBClient instance.
  • A second save of the same stream must expect the revision the first one predicted, or it throws commitConflict at once; so do two aggregate types whose stream names collide.
  • Each usecase's EventMetadataContext<M>.withValue value travels with that usecase's events; repositories with different Metadata types can save in one scope.

Rules inside the block

  1. No nesting. withUnitOfWork inside a scope throws operationNotAllow and leaves the outer scope alone. A usecase does not call withUnitOfWork; it belongs to the handler. When two handlers share logic, extract a function that does not open a scope and let each handler wrap it.
  2. Do not do/catch a usecase's error inside the block. To return a normal failure output, call try work.fail(error) and return. What goes wrong otherwise is a usecase that saves, then throws, and is caught: store errors in the default repository methods fail the scope automatically (BC4), and this rule covers the rest.
  3. Do not move a save into Task { … }. A task that is not detached inherits the scope; a save it reaches after the block ended throws operationNotAllow, never writes directly and never joins a batch that was already committed. Await everything before returning.
  4. Publish after the commit. A usecase that calls EventBus.publish right after save publishes before the commit inside a scope; use if let work = UnitOfWork.current { try work.onCommitted { … } } else { … } (BC2).
  5. Different aggregates may run concurrently, the same one may not. async let and TaskGroup over different aggregates are fine; when two tasks both find the same aggregate before either saves it, the second save throws commitConflict.
let quoting = try await withUnitOfWork { work in
    let quoting = try await createQuotingCaseService.execute(
        input: .init(operatorId: input.operatorId, name: input.name))
    try await openBillingAccountService.execute(input: .init(for: quoting.id))
    try work.onCommitted { try await notifier.send(.quotingCreated(quoting.id)) }   // after the commit
    return quoting
}

Projections run on subscription runners, not inside a scope

Do not run a projector synchronously inside withUnitOfWork Every read inside a scope through a KurrentStorageCoordinator over the same client instance as the scope's writes sees the staged events, including an EventSourcingProjector called from the block. Read model snapshots go to another store and are not part of the unit of work, so such a projector folds events that a failed commit never writes, and its snapshot runs ahead of the event store. Run projections on the KurrentProjection subscription runners: they run in their own task, outside any scope, and see only committed events.

Upgrade checklist

Fix what breaks the build first, then check the behaviour changes.

  1. Bump dependencies — swift-ddd-kit to from: "1.5.0"; a direct swift-kurrentdb requirement to 2.6.1 (SB3).
  2. Custom EventStoreClient — implement or forward identity and appendAtomically(_:); check that no appendAtomically deprecation warning is left (SB1, BC1).
  3. Exhaustive switch — handle consistencyViolations and atomicAppendUnsupported (SB2).
  4. Build + test — swift build, then run the test suite.
  5. Before adopting withUnitOfWork — move post-save publishing to onCommitted (BC2), give the repositories that write together, or read what the block saved, one KurrentDBClient instance (BC3), check metadata types (BC6), keep projections on the subscription runners, and follow the rules inside the block.

Reference KurrentDB version

KurrentDB 26.1 or later; CI runs kurrentplatform/kurrentdb:26.1.3 A unit of work that writes two or more streams needs AppendRecords, which KurrentDB 26.1 introduced; one stream works on older servers too. CI's kurrent-live-contract job runs KurrentLiveContractTests, including the unit-of-work suites, against kurrentplatform/kurrentdb:26.1.3 started with standard projections (KURRENTDB_RUN_PROJECTIONS=All, KURRENTDB_START_STANDARD_PROJECTIONS=true). Re-run those tests when you upgrade KurrentDB.
